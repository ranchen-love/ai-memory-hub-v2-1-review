# Hub 2.1 protocol

The release version is 2.2.0. The 2.1 vault stays readable without rewriting stored records. JSON documents use schema version `2.1`. A local instance is one audience and one sensitivity class: public, internal, private, or restricted. Use separate storage and OS identities or storage principals for different audiences. Record IDs are case-sensitive portable ASCII identifiers. The tuple (instance, kind, id, revision) identifies an immutable revision. Kind is session, asset, project, or memory. Revision starts at one. Writers editing an existing ID supply the revision they read. Identical retries are safe. A source carries a provider, an evidence kind and an opaque locator, never credentials. The user grants authority separately from claims in the payload.

- Sessions have an L0 index, optional L1 summary, optional L2 checkpoint, and separately authorized L3 visible messages. An authorized L3 query selects the newest raw-bearing revision at or before the requested session revision. The response keeps session and raw revision numbers distinct and returns the original raw source. L2-only updates add no raw body. L2 is versioned. Incremental checkpoints append list entries and replace selected scalar fields, preserving earlier revisions. Every L2 revision carries evidence and exact asset-version references when known.
- Projects represent current project status and timeline. Sessions may reference a project before its state record exists. Handoff includes current project state, associated session checkpoints, timeline and asset availability. The recipient must verify sources and reauthorize access. Handoff omits L3 and storage credentials.
- Long-term memory has an explicit review status. Session text never promotes itself to accepted memory. The automatic importer only writes candidate memory. Weekly reconciliation reports duplicate and conflicting candidates for review.
- File records distinguish content-addressed blobs from observed external links. Blob availability is derived by checking bytes. Link status is expired, reported, or unverified and carries its provenance. The default implementation makes no outbound link requests.
- Adapter capabilities are explicit. Local grants bind one adapter to one selected path. Event and scheduled entry points are invocations, independently gated by policy. Scheduler installation and provider authorization are separate facts. Batch receipts track applied items transactionally. Failed items remain pending and retryable.

Offline transfers use a separate 2.2 ZIP envelope. It contains canonical handoff JSON, a [digested manifest](../schemas/transfer.schema.json), and only individually selected Vault file versions. A same-sensitivity receipt binds the digests to the project and records the local verified payload. The receiving side derives file availability from its own Vault. L3 stays in the originating Vault.

SQLite serializes writers and atomically records revisions and import receipts. The file vault streams, hashes and stages local blobs, then atomically publishes a blob before the metadata transaction commits. Interrupted runs can leave unreferenced blobs but never committed references to an unpublished blob. The next identical import can reuse a verified orphan. Back up a quiesced instance directory as a unit. Instance parents must be trusted local paths. Source repositories may be mutable, so use a user-controlled staging directory if you cannot trust all workspace writers. Do not put SQLite or the local blob backend on a network filesystem.

An instance refuses incompatible database versions. Upgrade a disposable restored copy first, verify and then switch the pinned core and instance together. Preserve the previous core and backup for rollback. Never run concurrent versions against one database. An application integrating the core should select an exact source revision and verify its package file hashes.
